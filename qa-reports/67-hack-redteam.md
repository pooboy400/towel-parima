# 67-hack — گزارش هکر قرمزتیم (باتری نهایی — فازهای ۳–۶)

**تاریخ:** 2026-09-26 · **هدف:** فیکس‌های فاز ۳ (SEC/BUG)، فاز ۴–۵ (CSP/XSS) و فاز ۶ (INFRA-06/09) فروشگاه towel-parima
**محیط:** سرور dev `:3000` · PostgreSQL سندباکس (scripts/pg.sh) · NODE_ENV=development
**قواعد رعایت‌شده:** هیچ ردیف User/Session غیر از کاربران ساختهٔ خودم (نشان `redteam67-`) دست نخورد · رمز ادمین خوانده/چاپ نشد (فقط مقایسهٔ هش) · هیچ ویرایشی در src/ · بدون commit/push · بدون /admin/settings · cleanup فقط ردیف‌های نشان‌دار خودم
**اسکریپت‌ها/شواهد:** `qa-reports/tmp-67/` (attack-coupon.ts · attack-victim.ts · attack-origin.sh · probe-runner.sh · cleanup-67.ts · نتایج JSON/TXT)

> ⚠️ **رویداد محیطی (افشای شفاف):** سرور dev در میانهٔ جلسه (۱۴:۲۷) مرده بود (connection refused؛ لاگ نشان می‌داد یک تلاش راه‌اندازی دیگر بدون DATABASE_URL شکست خورده). طبق ممنوعیت، «ری‌استارتِ سرورِ روشن» انجام نشد — سرورِ **خاموش** با همان دستور رسمی و DATABASE_URL درست بالا آورده شد (لاگ append شد، چیزی truncate نگردید) تا حمله‌های HTTP قابل اجرا باشند. سرور در پایان سالم (health 200) تحویل شد.

## حملهٔ ۱ — رقابت کوپن perUserLimit (سرویس‌لول، مسیر کامل placeOrder)

**روش:** برخلاف باتری ۶۰ که `consumeCouponInTx` را مستقیم صدا می‌زد، این‌بار **کل زنجیرهٔ تراکنشی `placeOrder`** (رزرو موجودی + مصرف کوپن زیر `SELECT … FOR UPDATE` + Outbox) با تراکنش‌های همزمان حمله شد. کوپن‌های ATTACK با FIXED=1000 و usageLimit=null ساخته شدند تا فقط سقف per-user محک زده شود.

**A) مهمان — کوپن perUserLimit=2 · ۱۵ سفارش مهمان موازی:**
| سنجه | مقدار |
|---|---|
| تلاش | 15 |
| موفق | **2** |
| رد (DomainError) | 13 · همه `COUPON_INVALID` («ظرفیت این کد برای خرید مهمان پر شده») |
| ردیف CouponRedemption با userId=null | **2** |
| usedCount نهایی | **2** |

→ دقیقاً ۲ — سبد گمنام مشترک مهمان‌ها (ADR BUG-02) زیر قفل ردیف (BUG-01) در برابر ۱۵ رقابت همزمان نشت نداد.

**B) ترکیبی — کوپن perUserLimit=3 · ۵ کاربر ساختهٔ خودم (۴ تلاش هرکدام) + ۸ مهمان = ۲۸ تراکنش همزمان:**
| سنجه | مقدار |
|---|---|
| موفق کل | **18** |
| رد | 10 · همه `COUPON_INVALID` (تلاش چهارم هر کاربر + ۵ مهمان مازاد) |
| سهم هر کاربر | ۵ کاربر × **دقیقاً ۳** (groupBy: {3,3,3,3,3}) |
| سهم مهمان‌ها | **دقیقاً ۳** |
| usedCount | 18 = 15+3 (سازگار) |

**رأی: 🛡 DEFENDED** — هر دو سقف دقیقاً روی مرز انتظار؛ هیچ oversell و هیچ خطای غیر DomainError.

## حملهٔ ۲ — جعل کوکی اثبات پرداخت (INFRA-09)

**روش:** یک پرداخت PENDING واقعی ساخته شد (سفارش مهمان `5598372938`، مبلغ ۲۸۴٬۰۰۰، `authority=MOCK-d1c21e963b75305d596658ff` — authority عمداً «نشت‌پذیر» فرض شد). سپس کوکی `prima_pay_proof` با الگوریتم‌های بی‌کلید جعل و به `/mock-gateway` ارائه شد. HMAC با کلیدِ نامعلوم تلاش نشد (غیرممکن) — طبق دستور فقط ثباتِ رد شدن.

| # | کوکی ارائه‌شده | نتیجه |
|---|---|---|
| 1 | بدون کوکی (baseline) | «تراکنش یافت نشد» · نشت کد/مبلغ: 0 |
| 2 | **sha256(authority)** — جعل الگوی قدیمی | «تراکنش یافت نشد» · نشت: 0 |
| 3 | SHA256 حروف‌بزرگ | رد · 0 |
| 4 | sha1(authority) | رد · 0 |
| 5 | md5(authority) | رد · 0 |
| 6 | هگز تصادفی ۶۴ (طول درست) | رد · 0 |
| 7 | **کنترل مثبت:** HMAC-SHA256 با کلید dev-fallback (ثابت مستند در کد، فقط توسعه) | **AUTHORIZED** — مبلغ + کد سفارش نمایش داده شد |

- کنترل مثبت اثبات می‌کند مسیر اعتبارسنجی/کوکی سالم است؛ رد شدنِ جعل‌ها «معنادار» است نه اتفاقی.
- **پروب تکمیلی:** `/checkout/success?code=5598372938` با کوکی جعلی → تنها «اکوی خودِ ورودی» در flight payload رخ‌داد (رشتهٔ JSON-escape از مسیر درخواستی)؛ صفر جزئیات سفارش (مبلغ/اقلام/وضعیت) → SEC-04 پابرجا.

**رأی: 🛡 DEFENDED** — sha256 بی‌کلید دیگر قابل محاسبه نیست؛ رد شدن یکنواخت + مسیر مجاز فقط با HMAC کلیددار سرور.

## حملهٔ ۳ — جعل Origin/Host (BUG-14) — ۱۳ پروب

**روش:** POST به `/api/health` با ترکیب‌های Origin/x-forwarded-host/Host دست‌کاری‌شده؛ انتظار: 403 ساختاریافته یا رد تمیز فریم‌ورک، صفر 500.

| پروب | نتیجه |
|---|---|
| P1 Origin خارجی + Host عادی | **403 JSON** `{"ok":false,"code":"FORBIDDEN_ORIGIN",…}` |
| P8b Origin پورت متفاوت (`http://localhost:8080`) | **403** |
| P3b زیردامنهٔ Host (`https://app.localhost:3000`) | **403** — wildcard زیردامنه‌پذیر نیست |
| P3c Origin منطبق با wildcard سندباکس (`evil.space-z.ai`) ولی Host خارجی | **403** — تطبیق دوطرفه (origin و host هر دو باید whitelist باشند) |
| P10 Origin خارجی + XFH سندباکس | **403** |
| P2/P9 Origin خارجی + XFH/Host جعلیِ هم‌راستا | 405 فریم‌ورک (گارد می‌گذرد — طبق طراحی XFH لایهٔ دیپلوی محترم است؛ INFRA-08 مسیر بانکی را از XFH مستقل کرده) · بدون 500 |
| P4 Origin: null · P7 Origin ناقص · P11 دبل‌پورت · P3 ترفند پسوند-پورت (`localhost:3000.evil.example.com`) | 405 تمیز فریم‌ورک — Origin غیرقابل‌پارس به فریم‌ورک واگذار می‌شود (رفتار عمدی proxy.ts) |

**تحلیل:** هیچ پروبی 500 نداد (هدف اصلی BUG-14). ترفندهای bypass واقعی (پسوند/زیردامنه/wildcard یک‌طرفه) همگی 403 شدند. پروب‌های «گذرنده» یا نامعتبرند (URL parse fail — مرورگر واقعی هرگز چنین Originی نمی‌سازد) یا مبتنی بر اعتماد به XFH که مرز امنیت پروژه نیست (منبع حقیقت = requirePermission + allowlist خود Server Actions در next.config).

**رأی: 🛡 DEFENDED**

## حملهٔ ۴ — فلود و تکرار `/checkout/callback`

**الف) فلود تجویزی:** ۲۵ درخواست موازی `?authority=HACK67-NOEXIST-i&status=NOK` → **25×307، صفر 500**.

**ب) اثبات کمی ریت‌لیمیت جدید (تکمیلی):** ۲۲۰ درخواست `status=OK` با authorityهای ناموجود یکتا در یک پنجره:
- پاسخ‌ها: **220×307** (همه تمیز) · صفر 500
- شمارش `console.warn` سرور («checkout callback domain error») در dev.log: **دلتا = دقیقاً 120** → دقیقاً ۱۲۰ درخواست اول از گارد رد شدند (سقف `publicApi=120/min`) و ۱۰۰ درخواست بعدی پیش از touch-DB توسط ریت‌لیمیت redirect شدند (بدون لاگ). سقف دقیقاً روی عدد پیکربندی نشسته است.

**ج) idempotency با authority واقعی:**
| فراخوان | پاسخ | اثر DB |
|---|---|---|
| NOK اول (PENDING) | 307 → /checkout/failed · 93ms | Payment **FAILED** · Order **CANCELLED** · رزرو ACTIVE=0 · Outbox `PaymentFailed` = **1** |
| NOK تکراری ×3 + OK-after-FAILED ×1 | 307 · ~12-16ms | **بدون هیچ تغییر** — payment همان FAILED، fail_events همان 1، سفارش همان CANCELLED |

→ صفر 500، صفر اثر مضاعف (§11)، رزرو دقیقاً یک‌بار آزاد شد (reserved واریانت به 0 بازگشت).

**یادداشت:** سقف per-IP مشترک است؛ زیر فلود، callbackِ یک کاربر واقعیِ همان IP هم throttle می‌شود (رفتار fail-closed با redirect به صفحهٔ failed — قابل قبول؛ در prod منبع callback بانک IP ثابت دارد).

**رأی: 🛡 DEFENDED**

## حملهٔ ۶ — راز در دیف (گرپ تجویزی)

**دستور تجویزی:** `git diff 35bc307~5..HEAD | grep -inE "password|secret|token" | grep -v …` → **47 hit، هیچ مقدار اعتبارنامه‌ای واقعی بینشان نیست:**
- نام تست‌ها (`password policy > رمز معتبر`)، شناسه‌های کد (`customer.passwordSet`، `payProofSecret()`)، نثر گزارش‌های حادثه
- ثابت `prima-dev-pay-proof-secret` (fallback توسعهٔ INFRA-09 — گیت‌دار به NODE_ENV؛ اعتبارنامهٔ هیچ حسابی نیست و در production fail-fast دارد)

**اسکن عمیق‌تر (بدون چاپ مقدار):**
- الگوی «رمز + توکن ۹-نویسه‌ای» → ۲ hit که هر دو جملهٔ توصیفی حادثه‌اند؛ مقایسهٔ هش: توکن **نه** با رمز جاری (فایل .secrets بیرون ریپو) برابر است **نه** با مقدار افشاشدهٔ قدیمی (در `git show e2791da:worklog.md` حاضر نیست) → نثر توصیفی، نه راز
- مقدار خام رمز ادمین فقط در e2791da (بیرون رینج تجویزی) بود؛ چرخش + redact در d928cc1 انجام شده؛ رمز جاری فقط در `/home/z/my-project/.secrets`
- `.env` ترک نمی‌شود؛ در src/ فقط پیام خطای «postgresql://…» باقی است (بدون credential)
- باقی‌ماندهٔ INFO (موروثی از قبل): URL dev دیتابیس در fallback `scripts/backdate-content-dates.ts` و `scripts/pg.sh` (کاربر/رمز سندباکس localhost)

**رأی: 🛡 DEFENDED** (با یادآور فرایندی موروثی: ریپو باید private شود و تاریخچه قبل از push scrub گردد)
